# Архитектура BLUEFORM: Nuxt и Express

## Цель

Магазин и админ-панель остаются в Nuxt. Отдельное приложение Express постепенно становится единственным владельцем API и правил магазина. На время перехода Nuxt продолжает обслуживать большинство действующих сценариев; запрос категорий уже передаётся в Express.

```text
Браузер → Nuxt (интерфейс, SSR, проксирование /api) → Express API → PostgreSQL
                              ↑                              ↓
                         cookies клиента              почта и хранилище
```

## Ответственность Nuxt

- Страницы магазина и админ-панели, компоненты, состояние интерфейса и доступность.
- Серверный рендеринг и получение данных для страниц; запросы при SSR должны учитывать сессию текущего пользователя.
- Тонкий прокси `/api` на Express для одинакового адреса сайта и API в браузере; он передаёт необходимые заголовки и cookies, включая ответы `Set-Cookie`, и не содержит правил магазина.
- Обработка отображения ошибок и состояний загрузки. Проверки интерфейса помогают пользователю, но не заменяют серверную валидацию.
- Служебные возможности сайта, относящиеся только к отображению, например метаданные страниц.

## Ответственность Express

- API каталога, корзины, избранного, аккаунтов, заказов и администрирования.
- Аутентификация, сессии, авторизация администратора и проверка прав на каждом защищённом маршруте.
- Проверка данных, расчёт сумм и остатков, оформление и отмена заказов, переходы статусов и журнал действий администратора.
- Работа с PostgreSQL через Prisma, миграции и операции с внешними сервисами.
- Единый формат ошибок и OpenAPI, генерируемый из схем и описаний реально подключённых маршрутов; Scalar отображает этот контракт.
- Ограничение запросов и другие меры защиты. Для cookie-сессий перед подключением браузерных запросов отдельно определить защиту от CSRF, безопасные атрибуты cookie и доверенные origins.

## Структура

```text
client/              приложение Nuxt
  app/               страницы, компоненты и состояние интерфейса
  server/            текущий сервер Nuxt, пока владеет магазинным API
server/              самостоятельное Express-приложение на TypeScript
  src/app.ts         сборка Express, документация и подключение модулей
  src/server.ts      запуск сервера
  src/middleware/    общая обработка ошибок и будущие проверки запросов
  src/modules/       модули по предметным областям
    health/          маршруты и контроллеры проверки сервиса
    catalog/         маршруты, контроллеры, сервисы и схемы каталога
shared/              общие определения категорий, пока они нужны обоим серверам
prisma/              общая схема и единственный набор миграций; два сгенерированных клиента
docs/                документация и планы
```

Каждый предметный модуль разделяет маршруты (`router.ts`), HTTP-обработчики (`controller.ts`), правила предметной области и доступ к данным (`service.ts`), а также Zod-схемы (`schema.ts`). При необходимости доступ к данным можно выделить в отдельный `repository.ts`; middleware для конкретной области располагается рядом с ней, общий — в `src/middleware/`. Не создавать пустые файлы заранее. TypeScript используется в клиенте и сервере. Во время переноса Nuxt и Express используют одну схему и базу, каждый со своим сгенерированным Prisma-клиентом. Единственный набор миграций остаётся в `prisma/migrations`; перенос ответственности за миграции в Express пока не завершён.

## Переход без потери данных

1. **Готова основа:** отдельный API с проверкой доступности и Scalar; работает параллельно с действующим магазином.
2. Подготовить интеграционные проверки текущих сценариев и согласовать формат ошибок и API-контрактов.
3. Подключить Express к существующей базе без пересоздания данных. Подключение и проверка готовности реализованы; перенос ответственности за миграции остаётся впереди.
4. Перенести Better Auth, учётные записи, сессии и гостевую корзину. Проверить совместимость cookie, доменов, SSR и настройки почты; проверить регистрацию, вход и объединение корзин. До переноса нельзя считать это готовым.
5. Переносить каталог, корзину, избранное и заказы по одному модулю с проверкой поведения и OpenAPI. Категории обслуживает Express; Nuxt проксирует этот маршрут. У каждого маршрута в конкретный момент должен быть один активный владелец для покупателей.
6. Расширять проксирование Nuxt → Express по мере переноса маршрутов; до переноса авторизации отдельно проверить входящие cookie и все `Set-Cookie`, SSR, защиту от CSRF и авторизацию. Перенос категорий сам по себе эти сценарии не проверяет.
7. Реализовать админ-панель и защищённые административные маршруты, затем убрать перенесённый старый код только после проверок.

Последовательность переноса можно уточнить при реализации: маршрутизация отдельных модулей и сессий требует отдельной проверки, чтобы не сломать текущий магазин. Не переключать все запросы `/api` на Express до появления соответствующих маршрутов.

## Локальный запуск основы

Используется Node.js 24 или новее. Из корня проекта:

```sh
npm --prefix server ci
npm run dev:server
```

Проверка: `http://localhost:3001/api/health`, готовность базы: `http://localhost:3001/api/ready`, документация: `http://localhost:3001/docs`, спецификация: `http://localhost:3001/openapi.json`. Это отдельный порт и отдельная документация; действующий магазин и его Swagger остаются на порту 3000. Проверка `/api/health` подтверждает только доступность Express; `/api/ready` выполняет проверочный запрос к PostgreSQL.

Контрактные проверки запущенных сервисов: `npm run test:contract`. Для локального запуска Express вне Docker нужно самостоятельно задать доступный `DATABASE_URL`: база в штатном Compose доступна внутри сети Docker, но не опубликована на хосте.

Для Docker: `docker compose up -d --build`. Сервис `api` запускается вместе с магазином, а Nuxt получает внутренний адрес Express через `NUXT_API_INTERNAL_URL`; при локальном запуске без Docker значение по умолчанию — `http://127.0.0.1:3001`. Интерфейс Scalar использует закреплённый скрипт с CDN, поэтому для открытия документации нужен интернет. Документация и health-маршрут сейчас доступны без входа; политику доступа к документации перед публикацией нужно определить отдельно.
